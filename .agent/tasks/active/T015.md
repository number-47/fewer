# T015: PR3 — Finder 动作快照隔离与 MainActor 边界

## 元信息

- 优先级：P0
- 状态：BACKLOG
- 推荐执行器：implementer
- 依赖：T013, T023

## Goal

消除 `FinderActionHandler.context` 和每次重建都会复用的 `openWithBundleIDs/nextTag` 串台风险，让每个可点击菜单项通过唯一整数 token 绑定构建时的 `FinderMenuContext + MenuCommand` 快照。

## Context

Finder 动作通过 XPC proxy 回调。现有代码已经说明 `representedObject` 不会可靠序列化；动作入口当前只安全读取 `tag/title`。因此不能把 session 对象设为 target，也不能依赖 `representedObject` 或标题反解命令。正确边界是：构建菜单时注册不可变动作快照，把唯一 token 写入 `NSMenuItem.tag`；回调先读取 tag，再 hop 到 MainActor 解析并执行。

## Scope

- `FinderSync.swift`、`FinderMenuAdapter.swift`、`FinderActionHandler.swift`
- 可放入 FewerCore 以便测试的 `FinderMenuActionSnapshot/Registry`
- `FewerCoreTests` 中的连续菜单和 token 生命周期测试

## Implementation steps

1. 定义不可变快照：`context + command`。所有叶子菜单项都注册快照并获得进程生命周期内不复用的正整数 token。
2. `FinderMenuAdapter` 只把 token 写入 `tag`；删除标题解析、每菜单重置 tag 和 `openWithBundleIDs`。
3. 所有 `@IBAction nonisolated` 入口只在 hop 前从 sender 读取序列化 tag；进入 `Task { @MainActor ... }` 后解析快照并调用 `perform(command:context:)`。
4. `FinderActionHandler` 删除可变 `context`；`refresh/openWith/createTemplate` 等辅助方法也接收显式 context/载荷。
5. Registry 必须 MainActor 隔离且有明确的有界回收策略；回收不能导致“构建第二个菜单后，第一个菜单仍可见却失效”。
6. 所有 `NSPasteboard`、`NSWorkspace` 和 `NSMenu` 操作留在 MainActor；异步文件移动只把 Sendable 值传出。

## Acceptance criteria

- [ ] 不存在 `FinderActionHandler.context`、`openWithBundleIDs`、标题反解命令或每菜单重置 token。
- [ ] 连续构建两个不同 context 的菜单，触发第一个菜单项仍使用第一个快照。
- [ ] `copyAs/openWith/createFromTemplate/paste` 均通过同一 token 机制绑定完整载荷。
- [ ] 非隔离回调在 hop 前只读取 tag；AppKit/剪贴板/Workspace 访问均在 MainActor。
- [ ] Registry 有溢出和回收测试，不无限增长、不复用仍有效 token。
- [ ] FewerCore 单测和完整 Debug 构建通过。
